# TASKS — Phase 3.6, the quiet week

This is the live list. `TASKS-phase1.md` through `TASKS-phase3-5.md` are historical records.

**Phase goal:** the tree becomes boring. Phase 3.5 shipped in one day — rewind, marks, cancellation, counsel, web — and none of it has been *lived in* yet. This phase is a week of daily use with no planned rows: friction found in the drives folds in here as it always has, gets fixed, and the list stays short. | 1 | herdr integration: the TUI reports its own lifecycle instead of being screen-scraped. herdr 0.8 gives each pane one status authority — Claude Code earns it through installed hooks; arc, owning its harness, earns it natively. When `HERDR_PANE_ID` is set, a fire-and-forget reporter (arc-core module, wired in the client) speaks newline-delimited JSON over the local socket (`HERDR_SOCKET_PATH`, else `~/.config/herdr/herdr.sock`): `pane.report_agent` with source `custom:arc`, agent `arc`, mapping Streaming → working, Disconnected → blocked, the idle prompt → idle — three states, the entire report vocabulary. `pane.report_metadata` carries the session name as title and running-job counts as tokens — presentation only; semantic state belongs to the interactive turn, never to background jobs. Reporting never blocks the UI, never surfaces its own failures, and is inert outside herdr; nothing touches the log — display only, no events, no proto change. Learned against the live server (0.8.0, protocol 19), none of it in the docs: the socket answers one request per connection then hangs up, so the pump connects per report; reports carry a `seq` the server remembers per source *across processes*, so seq is epoch-milliseconds, not a counter from zero; and a report outlives its process — quitting sends `pane.release_agent` (plus a metadata clear) or the pane wears arc's last state forever, so `run()` returns through a `shutdown` that flushes both with a 500ms cap. And the one the first real drive caught: `done` is not reportable — the server rejects the literal string, so a finished turn stuck at *working* and no notification fired; herdr derives done from a working→idle transition itself and clears it on pane focus, which means done-until-you-look and cancel semantics belong to herdr, and arc's own logic for them was deleted, not fixed. Verified in a scratch pane: idle against the live daemon, blocked against a dead port, authority released on `:q`, working→idle rendering as done replayed byte-for-byte at the socket. Protocol: https://herdr.dev/docs/socket-api/ | claude | done |

| 4 | dispatch bounces to the warm job. The continue-vs-dispatch words did not hold: the doctrine, both tool descriptions, and the handback tail all say continue, and the concierge still defaults to a fresh dispatch, throwing away the child's accumulated context. The extractor's precedent applies — the check moves from prompt to code. When a dispatch names a project where the parent already has a finished job of the same role, the engine refuses the JobRequest with an ordinary tool error naming that job and both ways past it: continue_job, or an additive optional `fresh: true` argument for a genuinely unrelated task. The candidate is the parent's most recent child whose *latest* handback reads finished — a job whose last word was stopped (cancelled, crashed) is never suggested, so cancelled stays stopped even after a resume — and an implement dispatch is never bounced toward a read-only analyze job, because the handback tail already routes that case to a fresh dispatch. The guard lives in `Engine::dispatch_job` beside a new projection query (`latest_finished_job`) keyed on the same `Job {id} finished.` prefix `record_handback` composes; the tool stays stateless, a failed lookup dispatches rather than blocks, and nothing touches the proto. | claude | done |
